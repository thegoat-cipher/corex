## SH-044 — bootstrap code cleanup/review

Three commits, each independently verified. **No behaviour changes**: the
compiler emits byte-identical IR to the original build on all 16 positive
corpus cases and on `selfhost/corexc.cx` (17/17, `cmp` clean).

### 1. Removed 70 redundant nested `unsafe` wrappers (`7a00a3f`)

`parser.cx` (10) and `codegen.cx` (60) wrapped function bodies in two
consecutive `unsafe {` blocks. Nesting is redundant because `semantic.cx`
only ever compares `unsafe_depth == 0`, and `gen_block` (`codegen.cx:1786`,
dispatched from `codegen.cx:1717`) emits no IR for a block. 208 lines
deleted, 0 added.

68 of the 70 had the outer body consisting *only* of the inner block; the
other 2 (`parse_expr`, `path_loaded` in `parser.cx`) had trailing statements
in the outer block. `parse_expr`'s inner block declares nothing; the only
declaration moved by the unwrap is `path_loaded`'s `q`, and the surrounding
block declares no `q`, so no shadowing or redeclaration changes.

Proof of no-op: rebuilding the cleaned source yields a **byte-identical**
Stage 1–4 (`644c22c5…`), i.e. the emitted IR does not change at all.

### 2. Deleted unreferenced helpers, merged duplicate bodies (`5d420d3`)

Dead functions — each identifier occurred exactly once in the whole
translation unit, i.e. only its own definition:

| File | Removed |
|---|---|
| `ast.cx` | `prog_add` |
| `parser.cx` | `expr_append`, `stmt_append` |
| `runtime.cx` | `rt_clear`, `rt_cstr`, `rt_env_or`, `rt_find`, `rt_hex` |
| `semantic.cx` | `tkind_of`, `type_is_aggregate` |
| `codegen.cx` | `fbrcond`, `freg`, `rt_buf_len` |

Duplicate bodies merged (byte-identical wrappers, same signature):

| Removed | Kept | Call sites updated |
|---|---|---|

| `ir_name(f, id)` | `reg_of(f, id)` | 1 |

Function count 244 → 229 (confirmed by `corex check`, which prints the count).
New fixed point `c6df4a37…`. Corpus 79 × Stage 1/2/3. IR output still
byte-identical to the `644c22c5…` compiler on the 17 inputs.

### 3. Dropped dead `Program` fields (`fca2d21`)

`Program.decls` and `Program.decls_tail` were only ever initialized to `null`
in `prog_init()`; nothing read or wrote them. The front end consumes
`(*prog).items` exclusively (`semantic.cx:1824`). Both fields removed.
`items_tail` was kept: it is written by `parse_program` and mirrors real
parser state.

New fixed point `f14f8724…`. Corpus 79 × Stage 1/2/3. IR output still
byte-identical to `644c22c5…` on the 17 inputs.

### `ck` / `type_ok` — reviewed and **kept deliberately**

`type_ok` (`semantic.cx:52`) checks that a `*mut Type` lies inside the arena
and that its `K` discriminant is in `0..23`. It has four call sites, each
with its own internal diagnostic: `check_expr` (`semantic.cx:590`,
"invalid expected type two"), `ck` (`semantic.cx:984`, "bad type from
subexpression"), `check_binary` (`semantic.cx:994`, "invalid expected type"),
and the pointer-arithmetic operand check (`semantic.cx:1060`, "invalid
operand type").

Findings:

* **Invariant currently holds.** `check_expr` returns `null` only when
  `e == null` (`semantic.cx:586`), and every non-null return is either
  `type_new`/`type_ptr`/`type_array`/`type_vec` output, a caller-supplied
  `expected` (already validated at entry), or `resolve_type` output.
  `resolve_type` returns `null` only for `null` input and otherwise returns
  an arena type with a rewritten kind. So for the call sites that exist, the
  failure branch is not reachable in a correct run.
* **But it is not dead code, and it is not free to remove.** The compiler is
  memory-unsafe. Without the guard, a corrupted `Type*` turns into an
  out-of-bounds read during typing instead of a diagnostic. The guard is the
  only thing standing between an internal bug and undefined behaviour.
* **Cost is unmeasurable.** `ck` is invoked 3,453 times per self-compile
  (measured by instrumenting a throwaway copy with a `static mut` counter).
  Replacing `type_ok`'s body with `return t != null;` changed `check
  selfhost/corexc.cx` from 20.4 ms to 20.6 ms — i.e. inside noise.

Decision: keep both, do not consolidate the four messages (that would change
diagnostic text, which is a behaviour change). This is the "justify" branch
of the task, with evidence above.

### Deliberately not changed

* `items_tail` on `Program` (written, unread today) — kept; it mirrors parser
  state and costs one store.
* The `K` variants `F32`/`F64` and other unreferenced enum variants — they
  are scheduled language surface (SH-019/SH-020), not dead code.
* The flat body indentation left in `parser.cx`/`codegen.cx` after unwrapping
  — reformatting 7k lines would bury the semantic diff; separate follow-up.
* Three `"internal: …"` messages remain distinct to preserve diagnostics.

### Net effect

`selfhost/` went from 7,721 to 7,344 lines (−377 net: 383 deletions,
6 call-site edits), 244 → 229 functions. Lines of pure noise, no semantic
change.

## SH-042 — reproducibility at `--opt 1..3`

### Question

`bootstrap.sh` pins Stage 2 == Stage 3 == Stage 4 at `--opt 0`. The pipeline
above IR is `llvm-as` → `opt -passes=default<ON>` → `llc -O{N}` → `cc
-nostdlib -static -no-pie`. The open question was whether the optimized
self-builds are byte-reproducible, and whether Stage 2 and Stage 3 are
expected to match at a fixed opt level.

### Answer

**Yes, each level is byte-reproducible and reaches its own fixed point.**
Hashes **must not** match across different `--opt` levels; they are a function
of LLVM's pipeline, not of the compiler.

Final numbers on this branch (`f14f8724…` is the `--opt 0` Stage 2/3/4):

| Level | Self-build hash (Stage 3 of that level) | Size (bytes) | Build wall |
|---|---|---|---|
| `--opt 0` | `f14f87247d01b955cea1f6b273ee6726f8b32e704fa9dccb8bc48e14bcfc6779` | 248,232 | ~0.33 s |
| `--opt 1` | `b86239f9916a1ffc966fc7d676eac727c22ae6fd717ae5cc85d4d87ead93fc73` | 219,360 | 1.59 s |
| `--opt 2` | `b69aff8ce62cf2f49d945220de88685cd49a9eb31630afe3a0044483cf18d478` | 234,800 | 2.11 s |
| `--opt 3` | `b9a089e7bbda54e96e9ae0e15a6f8400648bd731f202eca0839e2caf2d0f4154` | 504,968 | 5.56 s |

For each level N: `stage2(--opt 0)` building at `--opt N` twice gives the same
bytes, and that binary rebuilding the source at `--opt N` gives the same bytes
again (fixed point).

### Why the levels differ from each other

Expected, and not a determinism defect:

* `opt -passes=default<O1|O2|O3>` runs a different pass pipeline per level.
* `--opt 3` is 2.25× the size of `--opt 0` (.text 0x6f6c1 vs 0x3170e) because
  `default<O3>` inlines aggressively: `gen_call` grows from 25,374 to 92,551
  bytes. Symbol count is basically unchanged (235 → 232 functions; three are
  inlined/merged away).
* `--opt 1`/`2` are *smaller* than `--opt 0` (219 KB / 235 KB vs 248 KB) —
  dead-argument elimination and register allocation outweigh the inlining.

### Additional invariant found: cross-compiler parity

`stage1` (built by the Rust oracle) and `stage2` (built by Stage 1) produce
**identical** bytes when compiling the same source at the same `--opt` level,
for `--opt 1`, `2` and `3`. The bootstrap compiler therefore emits IR that is
codegen-equivalent to the Rust oracle's for this input — the opt-level
differences come entirely from LLVM, not from IR drift between the two front
ends. `repro-opt.sh` checks this and fails if it regresses.

### Where the determinism comes from

* Temp paths are `/tmp/corexc.<pid>.ll|.bc|.o` (`runtime.cx:492`), i.e.
  PID-dependent, but the path never reaches the object: the module header
  emits the hardcoded literal `source_filename = "corexc"`
  (`codegen.cx:2135`) rather than the input path, and there is no debug info.
  Confirmed empirically: repeated builds with different PIDs, a different
  CWD, a different `TMPDIR` and a different `-o` directory all produce the
  same bytes.
* The linker emits a build-id derived from content, and no timestamps.

### New gate: `selfhost/repro-opt.sh`

```
selfhost/repro-opt.sh [--corpus]
```

Needs `build/stage1` and `build/stage2` (run `selfhost/bootstrap.sh` first).
For each of `--opt 1..3` it asserts:

1. `repeat == self` — two builds by the same compiler are identical,
2. `fixed == self` — the optimized compiler rebuilds itself identically,
3. `oracle == self` — Stage 1 and Stage 2 agree (skipped with a note if
   Stage 1 is absent),

and optionally (`--corpus`) runs the 79-case suite with each optimized
compiler. It prints the hash table above and exits non-zero on any failure.
The failure path was exercised by forcing a mismatch: exit 1 with
`REPRODUCIBILITY FAILURE: optN: …`.

Runtime: ~37 s without `--corpus`, ~52 s with it.

CI: `.github/workflows/ci.yml` gained one step after the existing bootstrap
step:

```yaml
      - name: Optimized self-build reproducibility (--opt 1..3)
        run: ./selfhost/repro-opt.sh --corpus 2>&1 | tee "$RUNNER_TEMP/repro-opt.log"
```

The `--opt 0` gate in `bootstrap.sh` is **unchanged** (as required).

### Performance of the optimized compilers

`check` / `emit-ir` on the 7,344-line self source, best of 15:

| Compiler | `check` | `emit-ir` |
|---|---|---|
| `--opt 0` | 21.4 ms | 49.9 ms |
| `--opt 1` | 11.5 ms | 27.4 ms |
| `--opt 2` | 10.3 ms | 24.5 ms |
| `--opt 3` | 10.1 ms | 24.2 ms |

So `--opt 2` buys 2.1× frontend throughput for a 6.4× build-time cost
(0.33 s → 2.11 s); `--opt 3` adds nothing measurable over `--opt 2` and nearly
doubles the binary for 17× build time. Recommendation for future packaging:
ship `--opt 2` for the compiler itself.

### Limits

* Reproducibility is relative to the pinned LLVM (`COREX_LLVM_BIN`, 20.1.8)
  and the system linker. A different LLVM or `cc` will change the bytes; the
  property proven here is "same toolchain ⇒ same bytes".
* Only this one translation unit is exercised.
* The script rebuilds three times per level by design; it is a gate, not a
  benchmark.

## Residual risks

1. **Hash churn.** Any parallel workstream that recorded `644c22c5…` as the
   expected Stage 2/3/4 value will now see `f14f8724…`. The gate itself is
   self-checking (it compares stages, never a hard-coded hash), so only prose
   and hard-coded expectations need updating.
2. **Cross-compiler parity is asserted, not proven.** `repro-opt.sh` fails if
   Stage 1 and Stage 2 stop agreeing. That is desirable today, but if the
   Rust oracle's IR changes legitimately, the check will fire; relax it
   deliberately rather than silently.
3. **`Program` layout changed.** Only `items` is read, but a future change
   that starts using `decls` must re-add the field.
4. **Removed helpers are recoverable** from git (`0c55d59:`) if SH-026/SH-030
   want `rt_cstr`/`rt_find`/`rt_hex` back.
5. **`source_filename` is hardcoded** to `"corexc"` for every module
   (`codegen.cx:2135`), so `emit-ir` on any input claims to be compiling the
   compiler. Harmless without debug info and it helps reproducibility, but it
   is misleading and will matter once `-g` lands. Not changed here because it
   alters emitted IR; a follow-up should derive it from the input path and
   then re-measure determinism (the temp path must still stay out of the
   object).
